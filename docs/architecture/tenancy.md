# Tenancy and row-level security

Implements D11 and D40 (1), (2) for `CompanyAccess`, (3) and (4). Built in ticket 02a (#31). Later tickets added to it, each in its own section below: sign-in and the pre-authentication functions (02b, #32; D40, D48), audit (02c, #33; D50, D54), firms and their administrators (02h, 02i, 02j; D49, D50, D56), job queue tenancy and execution (02d, #34 and ticket 24, #27; D36, D53, ADR 0001).

## How isolation works

- **Company** is the tenant. **CompanyAccess(user, company, role)** says who may act in which company. Owners and staff have one row; accountants have one row per company they are authorised for. There is no bypass role.
- Every business table has a `company_id` and the same policy: a row is visible and writable only when its company is among the signed-in user's `CompanyAccess` rows. The policy applies to reads, inserts, updates and deletes, with a check so a row cannot be inserted for, or moved to, another company.
- Requests run as the database role `web`: not a superuser, no `BYPASSRLS`, and it owns no tables. Tables use `FORCE ROW LEVEL SECURITY`.
- The signed-in user reaches the database as the transaction-local setting `app.user_id`. `core.middleware.TenantContextMiddleware` wraps each request in a transaction and sets the role and the setting with `SET LOCAL`. A missing or empty setting matches nobody, so an anonymous request sees no company.
- The membership tables are read-only to the web role (a user sees only their own `CompanyAccess` rows). Writes to them are made by the operator commands (firms, accountants) and the invitation functions (staff).
- Company-level authorization is this layer. Action-level permission (who may approve, who may change a TIN) is the Django permission service in 02b (D40 (4)).

## Adding a tenant table

This applies to the `backend/myinvois/` app too (D61 (4)): each of its tables follows these steps, and its app label is fixed before its first migration. `core` imports nothing from that app.

1. Subclass `core.models.TenantModel` (it adds the `company` foreign key).
2. In the migration that creates the table, add `core.rls.enable_tenant_rls("app_table")` straight after the `CreateModel`. It grants the web role access to that table and applies the policy.
3. Use `GENERATED ... AS IDENTITY` ids, which Django's `BigAutoField` already does. A separate sequence would need its own grant to the web role.

The web role starts with access to nothing and there are no default privileges, so a table added without step 2 is unreachable by it and forgetting the policy fails closed. Sessions and Django's own tables stay closed to the web role, except `django_session` (see "Identity and sessions"); users and jobs were opened by their own policies in 02b and 02d. A schema test fails if the web role can use any table that is not under forced row-level security.

## Roles and deployment

- Migrations create the `web` role without a login. If it already exists (roles are cluster-wide), they reset it to `NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS` and stop with an error unless those attributes hold. They must run as the table owner, never as `web`.
- For production, the application should connect with a login role that is a member of `web` and owns nothing (`CREATE ROLE app LOGIN PASSWORD ... IN ROLE web`), while migrations run with the owner's credentials. The middleware also drops to `web` on every request, so a connection made with the owner's credentials (as in development and tests) still cannot skip row-level security while handling a request.
- The user and session lookup that happens before the middleware runs as the connection's own role. The user table has its own policy and a narrow pre-authentication lookup function (02b, below).
- The web role reads only its own row of the user table and uses the session table (see the 02b section below). It reads and queues jobs for its own companies only (see "Background jobs").
- A streaming response is read after the middleware returns, outside the web role and its transaction. Do not query tenant data lazily inside a streamed response.

## Threat model and limits

- **The identity is a mutable session setting, and the role switch can be undone.** Any code running as `web` can execute `SELECT set_config('app.user_id', ...)` and so impersonate another user. It can also run `RESET ROLE`, which returns the session to the role the connection was made with, and what that role can do depends on what it is:
  - A **superuser** or a role with `BYPASSRLS` ignores row-level security entirely, `FORCE` or not. If the application connected as one, injected SQL could simply `RESET ROLE` and read every tenant's data.
  - An ordinary **table owner** is subject to `FORCE ROW LEVEL SECURITY` like anyone else on the tenant tables that later tickets add, so it does not see other companies' rows there by default. It keeps DDL rights, so it can alter or drop the policies and disable row-level security, or grant itself access, and then read everything. On `core_user`, `core_company`, `core_companyaccess` and the token and throttle tables it is already let through by the `definer_functions` policy (see 02b below), so it sees all their rows without any of that.
  - A login role that is only a member of `web` has nothing stronger to go back to, so `RESET ROLE` gains nothing. That is the production setup.
  In development and tests the connection is the owner's (and a superuser's in the Docker stack) and only the per-request switch protects tenant data. Row-level security protects against mistakes (a missing filter, a wrong query) and not against an attacker who can run arbitrary SQL as `web`.
- **SQL injection is the main threat to this design.** An injected statement could impersonate another user. Defences: parameterized queries and the ORM only, no string-built SQL, no raw SQL that includes request data, review of any `.raw()` or `cursor.execute()` use. Row-level security backs these up; it does not replace them.
- **Transaction-local only.** The setting and role are applied with `SET LOCAL` inside the request's transaction and reset explicitly at the end, so they cannot leak to the next request on a pooled connection. Code must not start work on the connection outside that transaction and expect the identity to apply.
- **Superusers bypass row-level security.** Nothing on a request path may connect as one. Development and test connections use a superuser but switch to `web` before touching tenant data.
- **Per-request cost.** The policy runs a subquery on `CompanyAccess` for each tenant table. This is acceptable at pilot size and the lookup is indexed through the unique constraint on `(user, company)`.

## Go-live prerequisite: production database login role

This is not built in ticket 02a and is mandatory before any real client data is stored. Provisioning must create a login role for the application that is a member of `web` and nothing else (no superuser, no `BYPASSRLS`, no ownership of tables or schemas, no other role memberships), keep its credentials in the secrets service and out of the repository, and run migrations with a separate owner role. A check at deployment should confirm the application's connection is not a superuser, does not bypass row-level security and owns no tables. Until then the repository's development and test connections, which use the owner, must not be treated as production-safe.

## Sign-in, invitations and the functions that run before anyone is identified (02b, #32)

Implements D40 (2), (4), (5), (7) and D48 for staff and accountants. Owner self-registration is #67.

**Users and roles.** `core.User` signs in with an email address (stored lowercase, unique ignoring case) and an Argon2 password. The role is on the `CompanyAccess` row, and a partial unique index allows one `owner` row per company. Owners and staff have one row; a firm accountant has one row per company of their own firm, added when the company is created (`core.services.create_company_with_owner`) or when the accountant is created (`manage.py create_accountant`). Accountants are never created or invited by a client (D48); in a firm they are created by its firm administrator (D49, ticket 02i, #74). Several firms are supported (D49): the code that grants every accountant every company is replaced by one that grants only the company's own firm's accountants (ticket 02h, #72, "Firms" below).

**Who may do what.** `core.permissions` holds the action-level rules (D40 (4)): `ACTIONS` maps an action to the roles that may perform it, `require` raises 403 in a view, and `{% can "action" company as allowed %}` offers the same check in templates. Register a new protected action in `ACTIONS`. A company the user cannot reach is a 404, so its existence is not revealed.

**Why functions.** Before anyone is signed in the web role has no identity, so row-level security shows it nothing. Sign-in, password reset and invitation acceptance therefore go through narrow `SECURITY DEFINER` functions owned by the table owner, each with a pinned `search_path`, executable by `web` only:

| Function | Returns | Notes |
|---|---|---|
| `auth_lookup(email)` | id, password hash, active flag | exact match, case-insensitive; nothing else about the user |
| `start_login_attempt`, `clear_login_failures` | allowed / nothing | counts an attempt before the password is checked; only a SHA-256 of the email is stored |
| `create_password_reset`, `token_is_valid`, `complete_password_reset` | bool / user id | at most three links an hour per account |
| `create_invitation` | whether one was created | checks inside the database that the signed-in user owns the company; the role is fixed to staff; at most 20 a day per company; an address that already has an account gets none and the caller is not told |
| `accept_invitation` | user id | creates the user and the membership in one transaction |

The web role has no direct access to `core_authtoken` or `core_loginfailure`, and may read only its own row of `core_user` (it needs the password hash to validate the session). It cannot create, change or delete users.

**Forced row-level security and the owner.** `FORCE ROW LEVEL SECURITY` also hides rows from the table owner, and the functions run as the owner, so each table the functions touch has a `definer_functions` policy naming the migrating role (`core.rls.owner_policy_sql`). It opens nothing to `web` or to a login role that is a member of it. Verified against a non-superuser owner: the migrations run, and every function works under forced row-level security.

**Identity and sessions.** The middleware takes the user id from the session and sets it as the database identity, then loads the user under that identity. If Django rejects the session (the password changed, or the user was deactivated), the identity is dropped again, so a stale session keeps no access to tenant data. Loading the user is itself a query that row-level security restricts, which is why the identity is set first. Sessions are stored in `django_session`, which the web role can use; it holds a session key and a signed blob naming a user id, no tenant data, and is the one listed exception to the rule that every table the web role can use is under row-level security. Django's `last_login` update is turned off, because the web role cannot write the user table and nobody is identified yet at sign-in; sign-ins belong in the audit trail (#33).

**Throttling.** Five sign-in attempts for an address in fifteen minutes lock that address, including addresses with no account, so the lock does not reveal which exist. The address is reduced to its key inside the database with the same `lower()` the lookup uses, so every spelling that signs in as one account (upper case, the Turkish dotted İ) shares one count. Each attempt is counted under a per-address lock before the password is checked and a successful sign-in clears the count, so parallel requests cannot all pass the check. Known limits: anyone who knows an address can lock its owner out for fifteen minutes, and there is no limit per client address, because that needs the deployment's proxy settings to be trustworthy (go-live, #39).

**Links.** Reset links last at most an hour and invitations at most a week; the functions cap the expiry whatever the caller passes. Tokens are random, stored only as a SHA-256 hash, single use, and indistinguishable when unknown, expired or used. A reset needs an active account. The functions accept only an Argon2 password hash. Tokens expired for more than thirty days are deleted whenever a new one is created. A password change ends the account's other sessions, because Django ties a session to a hash of the password. Links are built from `BASE_URL`, never from the request's Host header. Known limits: the reset form sends mail only for real accounts, so response time can reveal which addresses are registered, and three requests an hour per account can be used to delay that account's own reset. Both need a queue for outgoing mail (#27) to close.

**Two-factor authentication** is a go-live blocker (D40 (7)) and is not built here. Sign-in ends in one function, `core.signin.complete_sign_in`, which is where it plugs in.

**Not tenant tables.** `core_user`, `core_authtoken` and `core_loginfailure` have no company id. They are reached only through the functions above and, for the user's own row, the policy on `core_user`, so the standard tenant helper does not apply to them. The membership tables hold the company link.

**Deployment settings that matter.** `ENVIRONMENT` must be set to something other than `development` in production: it turns on secure cookies and the `SECRET_KEY` check. HSTS, SSL redirects and the proxy header are not configured yet. All of this is part of the go-live work in #39.

**Firm portal language.** The firm portal is English only (pilot spec, "Languages"), but the sign-in and company pages are shared and follow the browser's language. Fixing an accountant's language belongs with the firm portal screens.

**Firms (D49, ticket 02h, #72).** A `Firm` is an accounting firm. Every company has exactly one (`Company.firm`, not null, foreign key with PROTECT), and every firm accountant belongs to exactly one (`User.firm`; a check constraint refuses an accountant without a firm). Firms are created, and accountants are created inside them, only by operator commands (`create_firm`, `create_accountant EMAIL FIRM`, `move_company COMPANY_ID FIRM`), never through the web: the web role has `SELECT` on `core_firm` and no write right on firms, on the firm links or on the user and membership tables, and no route creates them. Firms are named uniquely, ignoring case, and the commands find them by name.

*Access follows the firm, through data.* An accountant reaches a company only through a `CompanyAccess` row, as before; there is no bypass role and no new policy on tenant tables (D40 (1), (2)). The firm decides which rows exist: creating a company for a firm grants rows to that firm's accountants, creating an accountant grants rows for that firm's companies, and `move_company` deletes the old firm's accountant rows and adds the new firm's (owner and staff rows are untouched). An accountant of another firm therefore gets 404 for every company page, as for any company they cannot reach. `User.is_accountant` stays the marker that an accountant created before any company still receives the firm's later companies. Only the services write them, as the table owner, and migration 0022 makes the database refuse any that do not match.

*Taking turns.* Creating a company, creating an accountant and moving a company each lock the firm rows involved (`select_for_update`, in primary-key order) before they read who belongs to the firm and write access rows, so a move cannot race a new accountant of the old firm into a stale row. The order is the same everywhere to rule out deadlocks: firms first, then the company (a move locks it and re-checks which firm it is in; if another move got there first it stops with `CompanyChanged` and the operator looks again), then, at commit, the company and user rows the access check holds. A move that waited behind another therefore never holds the company while waiting for a firm. Any later path that sets `User.firm`, deactivates or moves an accountant (02i, #74) should go through the same services, and should skip deactivated accountants when granting access.

*The database keeps the two together (migration 0022).* An `accountant` row in `core_companyaccess` is valid only if its user `is_accountant` and the user's firm is the company's firm. Three deferred constraint triggers on `core_companyaccess` (a row written), `core_company` (`firm_id` changed) and `core_user` (`firm_id` or `is_accountant` changed) run one `SECURITY DEFINER` function, `accountant_rows_match_firm()`, that refuses the transaction if any accountant row breaks the rule. This holds for every writer that runs triggers: the services, a shell, a later admin screen, or raw SQL. The checks are deferred, so a move may delete, update and insert in any order and only the committed result is judged. While it checks, the function holds the company and user rows involved (`FOR SHARE`, in a fixed order), so a concurrent change to one of them waits for that transaction and is then checked against it, rather than both passing. Owner and staff rows are not tied to a firm. The migration refuses to run if existing rows already break the rule. What can still bypass triggers: `TRUNCATE`, `ALTER TABLE ... DISABLE TRIGGER` by the table owner, and a superuser setting `session_replication_role = replica`; none is available to the web or worker roles.

*The firm table.* `core_firm` is under forced row-level security. A user sees the firm named on their own user row, and no other, so an accountant sees their firm and a client sees none. A client-facing path must use `company.firm_id`, not `company.firm`: the client cannot read the firm row, so following the link raises `DoesNotExist`. The migration owner has the usual `definer_functions` policy so the operator commands can write it. The job worker has no access to it.

*Audit.* Assigning a company to a firm, and moving it, are entries in that company's trail: `create` on `company` when the company is created for a firm, `update` on `company` when it moves, `changed_fields` = `["firm"]` and the actor shown as `operator` (written by `audit.record_operator_event`). They name no firm and no value, so the company's owner who reads the trail learns that the firm changed, not which firms. The firm trail (D50, 02j, #75) is described under "Audit trail".

*Existing data.* Migration 0020 puts any company and accountant that exist before firms into one "Default firm"; with no data it creates nothing. There is no production data yet.

## Threat model for the pre-sign-in functions (independent review of PR #68)

The functions in the table above are executable by the web role, so what an attacker with arbitrary SQL as `web` can do through them is part of the threat model of D40 (3). Impersonating a signed-in user by setting `app.user_id` is the smaller part. The functions also let such an attacker create credentials that outlast the injection:

- **Take over any account by email address alone.** `create_password_reset` followed by `complete_password_reset` sets a chosen password on an account, accountants included, with no identity and nothing logged. The caller supplies the token hash and receives the effect, so the link is no protection against someone who can call the functions directly.
- **Create a staff user in a company** by setting `app.user_id` to an owner's id, creating an invitation and accepting it.
- **Read every password hash** through `auth_lookup`, and every session key from `django_session`, for offline cracking and cookie theft.
- **Learn which addresses are registered**, from the boolean results.

What limits this: expiry is capped and only an Argon2 hash is accepted, so a junk hash cannot be planted; invitations are fixed to staff and capped at 20 a day; the functions cannot create an owner or an accountant; and the audit trail (#33) is to record sign-ins, resets and invitations. What does not change it: generating the token inside the database would not help, because the caller would receive it. Closing the exposure completely needs token minting and mail in a different trust domain from `web`. Until then the defences are parameterized ORM access only, review of every raw query, and two-factor authentication (D40 (7)), which is why it blocks go-live.

**Roles and the owner.** A non-superuser table owner cannot `SET ROLE web` unless it is a member of `web`, so the middleware fails closed for it; the production login role is a member of `web` and not the owner. Migrations refuse to run if `web` is a member of any other role, and the definer functions use a search path that begins with `pg_catalog`.

## Decisions on residual risk (product owner, 2026-10-30)

- **Credential minting through the pre-sign-in functions stays open as an accepted residual risk** for the pilot build. It is not required to be closed before PR #68 merges. It is re-examined before go-live together with two-factor authentication.
- **Two-factor authentication is not built now.** It is done before go-live (D40 (7)). Its absence does not block PR #68.
- **A session security review is a go-live security requirement:** the session store the web role can read and write, session key handling (for example hashed keys or signed cookies), lifetime and idle timeout, and invalidation on password change and on sign-out everywhere.
- **Migration 0003 was edited after it merged.** Django records only a migration's name, not its content, so an environment that applied the earlier version stays consistent and does not re-run it; it simply does not get the added role check. Verified by migrating a database with the earlier 0003 and then applying this branch: it upgrades without error and `makemigrations --check` is clean.

## Audit trail (02c, #33)

Implements D40 (6). Entries are in `core_auditentry`: company, who (account id and a copy of the address), what, which record, which fields changed, and when.

**What is recorded.** Every insert, update and delete on a business table, written by a trigger; successful and failed sign-ins and sign-outs; and domain events that are not a row change (an approval, a submission) through `core.audit.record`. Nothing else: the audit trail of the assistant and exports belong to their own tickets, and signings are a log line, not an entry (D55).

**Adding a business table to the trail.** In the migration that creates the table, after `enable_tenant_rls`, add `core.audit.enable_audit("app_table")`. The table needs `id` and `company_id`. The trigger runs with the rights of whoever makes the change, so the signed-in user writes their own entry under the same row-level security as any other insert, and a change to a company the user cannot reach is refused. A change made with no signed-in user (an operator command, a job) is recorded with no actor. An update that changes nothing records nothing.

**What is never stored.** Only the *names* of changed fields, never their values, so an entry cannot hold a password, a token, a TIN or an amount. `core.audit.record` must not be given content either.

**Sign-in events.** One entry for each company the account belongs to, written by the `record_auth_event` definer function because nobody is identified at a failed sign-in. With no signed-in user the function writes only `login_failed`, and only by using up one counted attempt made in the last minute (`core_loginfailure.audited`, migration 0032), so a bare call writes nothing and one attempt gives at most one entry; a successful sign-in is recorded as the person who just signed in (`complete_sign_in` sets the identity), and a signed-in user can record only their own events (D54, #84). Accountant and administrator sign-ins do not go to company trails: with firms (D50) they go to the firm trail (ticket 02j, #75); owner and staff sign-ins stay in the company trail. Not recorded: attempts for an address with no account (there is nothing to attach them to, and they would let anyone grow the table) and attempts refused by the lock (they do not test a password). Both still count towards the throttle.

**Append-only.** The web role has `SELECT` and `INSERT` only. A trigger also refuses `UPDATE` and `DELETE` from every other role, the table owner included. `TRUNCATE` is not trapped: the web role has no right to it, and Django's test runner needs it. There is no page that changes an entry. Retention and export (7 years, D4; D50 (7)) will need a controlled path for the operator; it does not exist yet.

**Who may read.** Company isolation is row-level security (the standard company rule, for reads and inserts). Which entries a role may see is the permission service: the owner and the firm's accountants read the company's full trail at `/companies/<id>/audit/`; staff are refused it with a 403 and read only their own activity at `/companies/<id>/activity/`, which every role can open for themself. A company the user cannot reach is a 404.

**Written only as the caller.** The web role's insert policy requires the actor to be the signed-in user and the address to be theirs, so an entry cannot be written in someone else's name, and a database trigger sets the time, so an entry cannot be back-dated. A signed-in user may record only their own sign-in events through `record_auth_event`; the sign-in page therefore sends someone who is already signed in home, and a different account needs a sign-out first. A row moved to another company leaves an entry in both companies. `enable_audit` refuses a table without `id` and `company_id`, because the trigger would otherwise fail on the first write and block it.

**Limits.**
- Staff reading only their own activity is the permission service. Row-level security gives any web session the company's entries, so an attacker with SQL as `web` in a staff session can read the whole company trail, which is also true of every other tenant table (D40 (3)). Entries already written cannot be changed or removed by `web`.
- An attacker with SQL as `web` can still add entries of their own for the companies they reach, as themselves, and SQL as `web` can call the throttle function first and then `record_auth_event`, so `login_failed` entries for an existing address can still be forged with no ceiling (D54 (4)): the throttle functions take their window and limit from the caller, and the identity setting can be changed, so the throttle's 5 per 15 minutes holds only for the application. A bare call with no counted attempt writes nothing, and a counted attempt is proof for one minute. Pinned by `test_known_limit_sql_as_the_web_role_can_forge_failed_sign_ins_without_a_ceiling`. Nothing removes forged entries until the retention path of D50 (7) exists. The trail shows the newest 200 entries and has no paging, so a flood could push older ones off the page; paging and search are not built.
- A write by a role that has no right to `core_auditentry` fails and blocks the business write. The job worker may write the trail, only through the audit trigger and only as the system (see "Background jobs"); any other new role needs its own grant and policy.
- A read is recorded only by a screen that uses `audited_read`. A screen that shows company data to an accountant without it is not caught at runtime; the guard test catches it at review time, for routes under `/companies/` (see "Audited reads").

**Audited reads (D45, ticket 02g, #69).** Every successful view of a company's data by a firm accountant writes a `viewed` entry to the company trail: the accountant (id and address), the company, what was viewed (a record type and id, or a list such as `audit_trail`) and the database-stamped time. `changed_fields` is empty and nothing from the page is stored. Owners and staff are not recorded, and neither is a request that was refused, not found or anonymous, or a POST (only GET and HEAD are reads).

The mechanism is a view decorator, `core.audit.audited_read(target_type, id_arg=None)`, chosen over middleware because a screen names what it shows (a record id or a list) and a middleware cannot know that. The view's `pk` argument is the company; `id_arg` names the argument holding the record id. The role is the viewer's role in that company (`CompanyAccess`), not a property of the user. The entry is written after the view has built a 200 response; if writing fails the request fails, so nothing is shown unrecorded. A streamed or lazily rendered body is rendered after the entry is written, so such a screen is recorded even if the body then fails (over-recording, never a missed read). The web role writes it as the caller under the existing insert policy, so no grant or policy changed: adding the `viewed` action is a change to the model's choices only.

*Not audited: the companies list (decision of the product owner, ticket 02g).* `/companies/` shows an accountant the companies they are authorised for, with their role in each. That is the accountant's own access list, not a company's data, so it is not recorded; recording it would write an entry in every listed company's trail on each visit. Opening a company from the list is audited. Revisit if the list ever shows more than a name and the user's role.

Reloading does not flood the trail: the same accountant reading the same thing in the same company within `audit.VIEW_WINDOW` (5 minutes, measured in database time) is one entry. Two concurrent requests can both write one; that only duplicates, never loses, an entry.

*Guard.* `test_audited_reads.py` walks the URL configuration and fails for any route under `/companies/` that is neither decorated nor listed in `NOT_AUDITED` with the reason it shows an accountant no company data (today: the invite action, owner-only; "my activity", which shows only the signed-in user's own entries; and the companies list). A new accountant-facing screen therefore has to use the decorator or be exempted in review. The guard does not see screens outside `/companies/`; a screen built elsewhere must be added to the walk. The screens that exist today and are audited are the company page and the full audit trail.

**Firm trail (D50, ticket 02j, #75).** Events with no company, such as a firm created, an accountant or administrator added or deactivated, or a firm account's sign-in, go to a second append-only trail, `core_firmauditentry`, keyed by firm. It uses the same append-only and time-stamp trigger functions and the same read-and-insert-as-the-caller rule; the database lets a user read an entry only for their own firm, and only firm administrators are shown the page that reads it (`/firm/audit/`, 02i, #74). It is never mixed with a company's trail or its export. A company moved between firms writes entries in the company trail and in both firms' trails with one correlation id. The company trail carries the same correlation id (ticket 02k, #76): a nullable column, null only for entries written before it existed, whose database default is `audit_correlation_id()`, so the audit trigger, the worker and the ORM store it without their code naming it. `record_auth_event` reads it once and names it, so one sign-in has one id across every company it writes to. Firm events are written with `record_firm_event`, because the user table has no company or firm column for a trigger to use. A table that carries `id` and `firm_id` is put on the trail with `enable_firm_audit`, as `enable_audit` does for the company trail. An accountant's sign-in, failed sign-in and sign-out go to the firm trail through `record_auth_event`; owner and staff events stay in the company trail. An operator command writes its entries with the actor "operator". The correlation id is the transaction-local setting `app.correlation_id`, set per request by the tenant middleware and per job by the runner; work that is neither (an operator command) wraps its entries in `audit.correlated()`, and an entry written with none set gets a fresh id from the database. Job handlers run as the `worker` role, which has no access to the firm trail.

**Firm administrator (D49, ticket 02i, #74).** A firm-level role held on the user (`is_firm_admin` plus the firm), never on a `CompanyAccess` row and never together with `is_accountant`; both rules are check constraints. With no access rows, row-level security shows an administrator no client data, and every company page answers 404; deferred constraint triggers (migration 0027) make the database refuse any access row for an administrator and flagging a user who has one. The pages are under `/firm/` and are English only; `permissions.require_firm_admin` refuses everyone else with 403. The web role cannot write users, so adding and deactivating people are SECURITY DEFINER functions (`create_firm_person`, `deactivate_firm_person`, `firm_people`, migration 0026). Each checks inside the database that the caller is an active firm administrator, takes the firm from the caller and never from its arguments, locks the firm first (the same lock order as `services.py`), and writes its firm-trail entry in the same transaction. `create_firm_person` repeats what `services.create_accountant` does for the operator, because that service runs as the table owner; a test compares the two. A new person (and a firm's first administrator, from the operator command) gets a single-use password link at `/reset/<token>/`, valid 24 hours (`SETUP_LINK_HOURS`); the ordinary reset link stays one hour, and the "forgot password" form issues another. The function re-checks the caller after it holds the firm lock, so an administrator deactivated while waiting cannot go on to act. The last active administrator of a firm cannot be deactivated. The database still lets any user of a firm read the firm trail (migration 0023); the page limits it to administrators. This is a decided, application-level rule for the pilot (D56), not an oversight, and is re-evaluated with the go-live review of #39.

## Background jobs (02d, #34)

Implements D36 and ADR 0001 rules 1 to 3 and 6.

**The job table.** `core_job` carries `company_id`, null only for a system job that touches no tenant data. `core.jobs.enqueue(name, company=company, **payload)` takes the company as an argument, not from the payload: a payload key named `company_id` is refused, and `company` must be a `Company`. Queued from a request, the database checks the company against the signed-in user's `CompanyAccess` rows, so a user cannot queue a job for a company they cannot reach, and cannot queue a system job. The web role can read and queue jobs for its own companies and cannot update or delete any.

**The worker role.** `worker` is a group role like `web`: no login, not a superuser, no `BYPASSRLS`, a member of nothing, and it owns nothing. The migration creates it, forces those attributes onto an existing role, and refuses to continue if they do not hold or if any role (other than a superuser) is a member of both `web` and `worker`, directly or through group roles (one login holding both could switch between them and reach any company). The check runs at migrate time only, so the go-live provisioning (#39) must check it again for roles granted later. It must also confirm that the migrating role owns the database (the `REVOKE TEMPORARY` needs it), that no role has an explicit `TEMPORARY` grant, that PUBLIC has no `CREATE` on schema `public`, and that any restored or re-created database gets the same `REVOKE`. The production worker process connects with its own login role that is a member of `worker` and nothing else (go-live, #39), and `run_pending()` switches to `worker` with `SET LOCAL ROLE` for each job and puts back the role it found, as the request middleware does for `web`.

**The company context.** Before a handler runs, the runner sets `app.company_id` from the job's own `company` column. A tenant table created with `enable_tenant_rls(table, worker=True)` carries a second policy for the worker that shows only rows whose `company_id` equals that setting, for reads and writes, so a handler reads and writes only its job's company. Without `worker=True` the worker has no access to the table at all, which is the default: a table that holds secrets (credentials, signing metadata, 2FA) stays closed to every handler. A payload that names another company's record finds nothing, and with no company set (a system job) a handler sees no tenant row at all.

**What the worker can touch.** A job is claimed through the `claim_next_job()` definer function (migration 0033; `claim_job()` before it), which sees every company's pending jobs for that one call, locks one (`SKIP LOCKED`) and marks it running. Only the worker may execute it, and it answers only while the runner is claiming (`app.claiming`, on for that one call), so a handler that calls it gets nothing. The worker's own policies on `core_job` cover the job's company alone (system jobs when it has none), so while a handler runs it can neither see nor change another company's jobs. It may update only `status`, `error`, `attempts`, `finished_at`, `run_after` and `lease_expires_at`, never a job's company, name or payload, and cannot delete jobs (only the purge function of "Job execution" does, and only finished ones). It can queue a follow-up job only for the company it is running for. It reads its own company's row and nothing else about companies. It can write the audit trail only through the audit trigger, as the system for its company (no actor), and cannot read the trail. It has no access to users, tokens, throttle counts or memberships. The TEMPORARY privilege is revoked from PUBLIC on this database, so `web` and `worker` cannot create temporary tables; the database owner and superusers keep it. The audit trigger skips the user lookup when no user is signed in.

**Limits.**
- A handler is trusted code. It runs with the job's company context and can do everything the worker role can do for that company, including writing audited tables. The context is a session setting like `app.user_id`, so a handler (or SQL injected into one) can change `app.company_id` and then read and write another company's rows. Review of every handler is still needed, as ADR 0001 says; the column makes the context correct by construction for honest handlers, and does not confine a hostile one. The same holds for `app.claiming`: a hostile handler can switch it on and call `claim_next_job()`, and so see another company's oldest due pending job (its id, name and identifier-only payload) and take it, or call `release_expired_jobs()` and so return other companies' expired jobs early. The audit guard (`pg_trigger_depth() > 0`) stops a handler writing an entry by accident or by plain SQL; with temporary tables revoked from PUBLIC, and PUBLIC lacking `CREATE` on schema `public` (the PostgreSQL 15 default), a handler cannot easily raise the trigger depth itself, but treat it as a guard, not a barrier.
- Queuing does not look inside the payload. A job queued for company A whose payload holds an identifier from company B is accepted; the database only checks that the signed-in user may queue for A. The handler then finds nothing of B's (the context is A) and the job fails when it runs.
- Payload key names are not interpreted. Only `company_id` is refused, because it would look like the source of the company; a handler must never treat any payload value as a company.
- The web role cannot queue a system job (a job with no company). A flow that has no company yet, such as owner self-registration (#67), queues it as the owner role or through a definer function.
- The web role can queue any registered job name, with any identifier payload, for its own companies. A handler must therefore treat its payload as untrusted identifiers and check that the record belongs to its company, which the row-level security of its context already enforces for tenant tables.
- `enqueue` trusts its caller's `company` only as far as the database does: from a request, the signed-in user's access; from an operator command or a test, the owner connection, which is not subject to the check. A job queued by a non-superuser owner connection needs the owner policy this ticket adds on `core_job`.
- The job table has no admin screen, API or report; a test pins that the admin and any job route are absent.
- A job whose handler raises is recorded with the exception class only. Retry, backoff, leases and purging are in "Job execution" below.
- A role that owns no policy on a new tenant table (the owner, a non-superuser) cannot write it under forced row-level security; operator tooling that writes tenant data must run as `worker` or `web`.

## Job execution (ticket 24, #27)

Implements the second half of ADR 0001's table and D36's queue. Code: `core/jobs.py`, migration 0033.

**Claim, lease, outcome.** `run_pending()` first sweeps, then claims one job at a time. A claim is a short transaction of its own: `claim_next_job(now, lease)` marks the oldest due pending job `running`, counts the attempt (`attempts`), sets `lease_expires_at` (5 minutes, `LEASE_SECONDS`) and clears `run_after`. The handler then runs in a second transaction, so no row lock is held while it calls a slow service. The handler's database writes and the outcome (`done`, a retry, or `failed`) are one transaction. The outcome is written only if `status = 'running'` and `attempts` still equals the value returned by the claim (the fence). A worker that outlives its lease finds the job swept and perhaps claimed again, writes nothing, and its own database writes roll back (logged as "lost its lease").

**Sweep.** `release_expired_jobs()` returns every running job whose lease has expired to pending, with `error = 'LeaseExpired'` and a `run_after` backoff, or to failed once out of attempts. The lost attempt was already counted at claim. A job that crashes every worker is therefore failed after `MAX_ATTEMPTS`. Both functions answer only while `app.claiming` is on, as `claim_job()` did (which migration 0033 replaces with `claim_next_job()`).

**Errors.** A handler raises `jobs.TransientError` (retry up to `MAX_ATTEMPTS`, 5) or `jobs.PermanentError` (fail at once). Any other exception is unknown and retried up to `UNKNOWN_ERROR_MAX_ATTEMPTS` (3). Retries wait `BACKOFF_SECONDS * 2^(attempt - 1)` seconds (30, 60, 120, 240) through `run_after`. A handler that catches a database error and returns normally is failed at once (`SwallowedDatabaseError`): after the error its transaction is unusable. A job with no handler fails at once. A `BaseException` (the process is going down) records nothing, and the lease expiry recovers the job.

**Idempotent external calls.** A job is run again after a crash, possibly after its external call succeeded. A handler passes `jobs.idempotency_key(step)` (`job-<id>` or `job-<id>:<step>`, the same on every attempt, an identifier only) as `idempotency_key=` to every port call with an external effect: `email.send`, `ai.extract`, and the gateway's `submit` and `cancel`. The email and AI ports seeing a key twice do the effect once and answer as they first did. The MyInvois gateway is the exception (D58 (5)): LHDN has no idempotency key and answers a repeat with a 422 or `DV302`, so the key only guards our own worker, and `core/submission.py` records the invoice number and hash first and recovers the `uuid` by internal number. A job that makes several such calls names each with its own `step`. The fake email and AI ports de-duplicate by key, and every fake port, inside a job, refuse a call without one (`IdempotencyKeyMissing`). A real adapter must do the same; this is part of the port contract (`core/ports/interfaces.py`). The key is only as good as the provider's support: an adapter for a service with no idempotency of its own must record the key itself before the call.

**Logging.** A failed attempt is logged at error level with the job id, name, exception class, the file and line where it was raised, the attempt number and the resulting status. The message, the traceback and the payload are never logged.

**Failed jobs.** `jobs.failed_count()` and `python manage.py failed_jobs` give the number of failed jobs across all companies (`failed_job_count()`, executable by the worker only). The alert is set on it being above zero; wiring it to a scheduler and a notification is go-live work (#39).

**Purge.** The `purge_finished_jobs` system job deletes done and failed jobs that finished more than `JOB_RETENTION_DAYS` ago (default 30; the app will not start with less than 1 or a non-number) and queues its own next run for a day later. `python manage.py schedule_jobs` queues the first run and is safe to run on every deploy. Pending, running and recent jobs are kept. `purge_finished_jobs()` does nothing while a company context is set, so a company's job cannot call it by accident; as with `app.claiming` that is a guard, not a barrier against a hostile handler. Failed jobs older than the retention are purged too, so the alert covers failures inside the window only. If the purge itself fails for good, the chain stops and the failed count shows it.

**Limits.**
- The attempt cap and backoff are constants in `core/jobs.py`, not settings; only the retention is configurable.
- Nothing in the repository starts a worker loop yet; `run_pending()` is what a worker process will call, and the lease assumes it is called often enough to sweep (go-live, #39).
- Reversing migration 0033 is refused while any job is `running` (the old runner would never claim it again). Stop the workers and let their jobs finish or expire first.
- The lease is fixed (`LEASE_SECONDS`) and is not renewed while a handler runs. A handler that outlives it is swept and its job claimed again while it is still running. Its own outcome and database writes are then discarded (the fence), so what protects an external effect it already caused is the idempotency key alone. Keep a handler's external calls well inside the lease, or add a heartbeat when a real handler needs one.
- `schedule_purge()` checks and then inserts, so two deploys running `schedule_jobs` at the same moment can queue two purge chains. They only repeat a harmless delete; remove the extra pending job if it happens.
- A hostile handler can also write its own `lease_expires_at` and `run_after` (migration 0033 grants both), as it can write `attempts`.
- `attempts` is still writable by the worker role (migration 0017 granted it), so a hostile handler could reset its own count. Same class of limit as `app.company_id`.

## Document numbering (07b, #45)

Implements D18, D44, D59 (6), D60 (2). `core_documentsequence` is a tenant table (company id, forced row-level security, audit trigger), one row per company and document type (`invoice`, `credit_note`, `debit_note`, `refund_note`), holding the owner's prefix, starting number and the next number.

- **Taken once, at approval.** `core.numbering.allocate_number(company, type)` is called by the approval action inside its transaction. It locks the sequence row until that transaction ends, so concurrent approvals take turns, and a rolled-back approval never used its number. Drafts are unnumbered. A cancelled document keeps its number, and an approval repeated after 72 hours keeps the number it has, so neither calls the service.
- **Database guard (migration 0034).** A trigger allows an update only to add one to the counter, or, while no number has been issued, to restart the sequence with a new prefix and starting number. A sequence that has issued a number cannot be deleted. Jumping ahead, reusing or taking back a number therefore fails for every writer that runs triggers. The trigger cannot tell whether a +1 went with a document, so gaplessness also depends on the approval taking the number in the same transaction that stores the document, and on that document table (07c) enforcing a unique number per company and document type.
- **Configuration.** `configure_sequence` sets the prefix (at most 10 characters), the zero-padded width of the digits (0 to 10; 0 means none, so `INV-` with width 5 gives `INV-00123`) and the starting number, and is refused with `SequenceInUse` once a number was issued. The prefix and width are frozen with it, so one sequence never mixes formats; a change of prefix for a new financial year is not allowed (product owner, 2026-11-07). The caller checks the `configure_numbering` permission (owner only). A number is at most 20 characters for the SQL Account export (D51 (3)).
- **Audit.** Each number taken writes an update entry naming `next_number`, never its value.
- **Not built here.** The approval action, and the onboarding screen that enters the last used number (#23).
